# P2.1 ticket — durable reported/desired Twin state

Status: **implemented, final-review approved, and committed**.
P2.0 contract review and the Stage-1 delta report were approved. Final P2.1
review passed on 2026-10-05; P2.2 has not started.

1. Design additive **V21** schema for desired state keyed by
   `(deviceId,bindingId,optional subtarget)` with explicit
   `(deviceId,legacy:CapabilityType)` fallback. Retain current reported
   `digital_twins` rows/key and API fields. V17 already backfilled most legacy
   bindings; reconcile only provable one-to-one identity, never a key-name
   guess. Define multi-channel RELAY subtargets under one WRITE binding.
2. Add typed current desired value, source, request/command ID, requested and
   accepted times and dispatch state (deadline belongs to P2.4). Keep database as
   authority and hydrate cache on restart. Derive effective envelope from
   reported/desired; do not persist a free-standing effective value.
3. Refactor both manual and Rule SEND_COMMAND paths through one validated
   pre-publish acceptance service. In one transaction create an ActionHistory
   row in new `ACCEPTED_FOR_DISPATCH` state and desired intent; publish only
   after commit. Rollback leaves neither. Publish success becomes existing
   `SUCCESS`, publish failure `FAILURE` with desired retained. An accepted row
   left un-published by crash remains delivery-unknown; Phase 4 outbox/retry
   is explicitly not claimed. Preserve existing API `SUCCESS` meaning. Ensure
   publish-result and ACK updates are monotonic so a fast ACK cannot be
   overwritten by a later publish-result update.
4. Add approved additive fields to existing Twin DTO/API; preserve routes,
   `latest*`, `reportedState` keys, and legacy numeric wire behavior. No new
   history/quality/convergence engine in this ticket.
5. Test fresh and migrated DBs, numeric/boolean/enum/object values, legacy
   fallback, binding uniqueness and relay channels, manual/rule unification,
   rejected requests, transaction rollback, publish failure, crash-window
   delivery-unknown state, concurrent intent, and restart. Do not assume
   `READ_WRITE`; current model has separate READ and WRITE definitions.

Acceptance: command/ACK alone never mutates reported state; desired exists
only after validated durable acceptance; API compatibility and legacy/generic
integration suites pass.

Implementation notes: V21 uses a non-null canonical `target_key` and non-null
`subtarget_key`, with binding-vs-legacy XOR and a composite primary key; it
does not rely on PostgreSQL nullable UNIQUE behavior. `action_history.request_id`
is the existing primary key and desired state references it. Desired state does
not duplicate delivery status; the API reads status/ACK from ActionHistory.
Device-row pessimistic locking defines durable acceptance order. Rule actions
may originate inside telemetry's transaction, so command acceptance uses
`REQUIRES_NEW` and commits before publish. Post-commit MQTT ordering is still
not guaranteed without a future outbox/device sequence. Desired state is read
from the database on API requests—there is no memory-only desired cache—and
effective state is recomputed. Generic nonnumeric realtime/EventDetector null
assumptions were corrected narrowly. Existing `quality` remains unchanged.
