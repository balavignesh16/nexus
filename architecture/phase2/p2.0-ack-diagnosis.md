# P2.0 live relay ACK diagnosis (2026-10-03)

## Failure and proven boundary

The committed `simulator/tests/test_integration.py` selected the **first**
ACTIVE/SIMULATED device with RELAY/WRITE, without identifying which simulator
process owned that device. The running development database contained three
such devices: `ESP32-001` (`7fbb9b75-...`), `ESP32-ACTUATOR-01`
(`4e4ce0fa-...`), and `ESP32-SIM-002` (`71f49b2e-...`). The active grand
simulator log shows it provisioned/connected `ESP32-ACTUATOR-01`, not the
other two. A read-only broker-log check shows the last
`nexus-sim-7fbb9b75-...` connection closed at broker timestamp 1789502838,
while the current grand simulator `nexus-sim-4e4ce0fa-...` connected at
1791016446. Thus the former selector could publish to a device ID without
the current simulator subscriber. The prior relay test failed twice with no ACK.
It did not record its command ID, SUBACK, or MQTT trace, so those two failed
packets cannot be reconstructed retroactively; no unobserved packet claim is
made here.

A regression fixture with an orphan RELAY device before the running device
failed against the original selector (`orphan` selected), then passed after
the fix. A second fixture proves that absence of an explicit simulator
identity causes a skip rather than an arbitrary target. This is a
**device-selection defect**, not evidence of a simulator RELAY ACK defect.
The original test's unconfirmed subscription is a separate potential race;
this investigation did not prove that it caused the observed failure.

## Narrow fix

Live LED/RELAY tests now require `NEXUS_LIVE_LED_SERIAL`/
`NEXUS_LIVE_RELAY_SERIAL` identifying the actual running simulator device.
With a configured serial that is missing or lacks the capability, the test
**fails**; without configuration, it skips rather than producing misleading
live evidence. `NEXUS_LIVE_BACKEND_URL` and `NEXUS_LIVE_MQTT_PORT/HOST` allow
the same tests to run against isolated infrastructure. ACK semantics,
simulator publishing, backend ACK handling, timeouts and assertions were not
weakened.

## Isolated lifecycle evidence

Disposable Timescale/PostgreSQL on 15432 and Mosquitto on 11883 used separate
containers, tmpfs DB storage, and a separate backend on 18080 with unique
MQTT client ID. They did not use the development DB or broker. Provisioned
`SIM-ESP32-SIM-001` (LED) and `SIM-ESP32-SIM-002` (RELAY) were served by actual
`MQTTPublisher`/`SimulatedDevice` clients. An independent MQTT observer
received SUBACK before commands. The backend REST command path produced
ActionHistory request IDs that were identical to MQTT `commandId` values.

Representative RELAY command: device
`bbdf9dc3-4d26-48ca-ab11-600563e1b6da`, command
`a71f9b20-1b47-4e11-9069-5a32eb466525`, topic
`nexus/devices/<deviceId>/commands`, QoS 1, retain false, payload
`{"capability":"RELAY","command":"SET_STATE","value":{"channel":2,"state":false}}`.
The observer then saw `nexus/devices/<deviceId>/commands/ack`, QoS 1,
retain false, same ID, `ACCEPTED`; simulator channel 2 was false; backend
`GET /actions/history?deviceId=...` reported matching `requestId`,
`status=SUCCESS`, `ackStatus=ACCEPTED`. An equivalent LED example used
device `cf07d155-e955-431f-a153-01fbe2960266`, command
`65c030eb-259a-4c31-a4bc-5ca25ebfe694`, and value `true`.

The instrumented run: **10/10 LED and 10/10 RELAY**, all with command MQTT
observation, matching MQTT ACK, simulated actuator result, and persisted
ActionHistory ACK. After the selector fix, the original live tests were run
10 times each with explicit serials: **10/10 LED and 10/10 RELAY**. Focused
selection regression: 2/2. The 10-per-device sample shows the selected
simulator path works; it is not a long-soak reliability guarantee.

Post-fix `python validate_nexus.py --fast` passed. Its simulator suite had
55 passing tests and two **explicitly skipped** live LED/RELAY tests because
no simulator serial was configured for the development stack; those skips
are not counted as live ACK evidence. The separate isolated runs above are
the live evidence. The supervised application was subsequently stopped for
`python validate_nexus.py --full`, which **passed** (747 backend tests,
417 frontend tests, 54 simulator tests/three live-stack skips, deterministic
loop, isolated ACK, and restart smokes). The app was restarted and verified
healthy. Those skips remain separate from isolated live ACK evidence.

`ACCEPTED` means the simulated software accepted/applied its command. It is
not physical relay or LED verification, and P2.0 does not infer convergence.
