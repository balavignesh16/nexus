# P2.3 ticket — capability-specific Twin quality

Status: **planned, not implemented**. Depends on P2.1 identity; may use
P2.2 diagnostics but quality need not be stored as a transition.

1. Reuse existing positive `DeviceTemplateCapability.freshnessThresholdSeconds`;
   add an optional validated binding override. The current binding-configuration
   validator does not admit freshness metadata, so extend its schema explicitly.
   Enforce binding threshold <= template/system default, with documented system
   fallback and migration defaults.
2. Capture durable backend `receivedAt` at ingestion and derive
   GOOD/STALE/OFFLINE/UNKNOWN from it, current connectivity, and value presence.
   Invalid incoming candidates stay in ingestion diagnostics, not Twin quality;
   invalid persisted data is quarantined/UNKNOWN. Recompute on read/schedule
   and after restart using an injected clock.
3. Add `stateQuality` while retaining existing `quality` fields with their
   current fixed-age meaning for `/api/v1` compatibility. RuleEvaluator must
   continue reading **reported** values and reject non-GOOD current capability
   inputs by default; test both legacy and generic conditions. No quality
   score or new desired/effective Rule lookup is introduced.
4. Test threshold boundaries, null/zero/negative overrides, no observation,
   unknown/offline connectivity,
   future device eventTime, invalid candidate vs invalid stored value,
   binding narrowing, restart, realtime/UI display, and safety-rule gating.

Acceptance: a stale/invalid Twin cannot silently actuate a safety-critical
rule; existing reported values remain truthful and explainable.
