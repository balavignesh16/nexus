# P2.3 ticket — capability-specific Twin quality

Status: **implemented, final-review approved, and committed**. Uses P2.1 identity and P2.2
diagnostics; quality is derived at read/evaluation time and is not stored as a
transition.

1. Reuse existing positive `DeviceTemplateCapability.freshnessThresholdSeconds`;
   treat it as immutable template-version configuration once the template is
   referenced, preserving the existing composition lock. Add a dedicated
   optional validated binding override rather than JSON configuration.
   Enforce binding threshold <= template/system default, with documented system
   fallback and migration defaults. Existing devices retain their parent;
   overrides may tighten or be removed to inherit, but may not exceed it. A
   changed parent for future devices requires a new template identity serving
   as a new immutable revision; do not imply that the current optimistic
   `version` field forks a referenced template. The existing capability update
   API may change freshness only while the
   template is unreferenced; add no generic composition-editing path.
2. Capture durable backend `receivedAt` at ingestion and derive
   GOOD/STALE/OFFLINE/UNKNOWN from it, current connectivity, and value presence.
   Invalid incoming candidates stay in ingestion diagnostics, not Twin quality;
   invalid persisted data is quarantined/UNKNOWN. Recompute on read/schedule
   and after restart using an injected clock.
3. Add `stateQuality` while retaining existing `quality` fields with their
   current fixed-age meaning for `/api/v1` compatibility. RuleEvaluator must
   continue reading **reported** values and reject non-GOOD current capability
   inputs by default; test both legacy and generic conditions. No quality
   score or new desired/effective Rule lookup is introduced.
4. Test threshold boundaries, null/zero/negative overrides, no observation,
   unknown/offline connectivity,
   future device eventTime, invalid candidate vs invalid stored value,
   immutable referenced-template policy, unreferenced-template update, binding
   narrowing/removal, restart, realtime/UI display, and safety-rule gating.

Acceptance: a stale/invalid Twin cannot silently actuate a safety-critical
rule; existing reported values remain truthful and explainable.

## Implementation closeout

- V23 adds nullable, exact backend `received_at` and a dedicated positive
  binding freshness override. Existing rows deliberately remain UNKNOWN until
  a new accepted observation supplies receipt time.
- `FreshnessPolicy` centrally enforces inherit/default/narrow-only behavior;
  referenced template policy remains immutable through the existing lock.
- `TwinStateQualityEvaluator` derives GOOD, STALE, OFFLINE, or UNKNOWN with
  reason, evaluation time, receipt time, threshold, and connectivity evidence.
- Generic and legacy capability-backed Rule conditions require GOOD state;
  event-payload-only conditions retain their existing behavior. Match evidence
  includes the quality decision.
- Twin and onboarding/template screens expose quality and freshness policy,
  including a single nearest-boundary refresh timer rather than one timer per
  capability.
