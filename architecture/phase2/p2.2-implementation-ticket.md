# P2.2 ticket — Twin transition history

Status: **implemented, final-review approved, and committed**. Built on P2.1 state identity with
Flyway V22, canonical current-state reconciliation, transactional transition
history, after-commit projection/publication, the history API, and durable UI
diff mode.

1. In V22 first canonicalize reported current-state identity to
   `(deviceId,bindingId)` or `(deviceId,canonicalLegacyType)`: add `state_key`
   and legacy identity, enforce XOR plus `(device_id,state_key)` uniqueness,
   retain configured API key and last raw wire identifier as provenance, and
   key the cache by stable state identity. A binding can currently resolve its
   definition key plus configured `telemetryKey`, and legacy aliases can also
   duplicate rows. Reconcile each existing duplicate group by newest event
   time, then backend `last_seen`, then lexical external identifier; archive
   every losing row verbatim with reason before removing it from current state.
   Never use display name or fabricate a transition for reconciliation.
2. Add an indexed transition table with `transitionId`, device/state ID,
   controlled type/source, typed previous/new values and unit, applicable
   event/receipt/recorded times, correlation ID and proven command ID.
   `transitionedAt` is the injected-clock time the row is recorded within the
   transaction, not an exact database commit timestamp; it is durable only if
   the transaction commits.
3. Persist only meaningful reported typed value/unit/semantic-metadata changes
   and desired changes/clear. P2.4 may later add actual verification-status
   changes; P2.2 does not implement convergence. Newer same-value/unit/metadata
   telemetry refreshes current observation but is not a state transition.
   Replays/out-of-order/invalid
   candidates create no authoritative transition. Preserve source diagnostics
   separately. The current semantic-metadata allowlist is empty. Include
   superseded intent in history. A newly accepted same-value desired command
   does create `DESIRED_STATE_CHANGED` because command identity, acceptance
   time, and source form new intent; same-value newer reported telemetry does
   not create `REPORTED_STATE_CHANGED`.
4. In the device-row-locked transaction persist raw/current state and history.
   After commit update the stable-identity cache, then Twin realtime, domain
   event, and Rule evaluation. Cache projection failure evicts the affected
   key and forces PostgreSQL read-through; all post-commit failures are logged
   without rollback or automatic retry. Move accepted-telemetry realtime and
   successful TELEMETRY trace publication after commit too.
5. Implement the proposed paginated, filterable `/api/v1` history route only after
   contract approval. Use stable descending `(transitionedAt,transitionId)`
   recorded-time cursor order; encode cursor version/time/UUID/filter
   fingerprint in bounded URL-safe base64 and reject malformed/mismatched
   cursors. Validate limits/filter combinations. Index device/time and
   device/binding/time queries; add command index only if queried. Define
   retention and audit implications before deployment.
6. Test alias reconciliation, duplicate/out-of-order telemetry, concurrent
   first observations, post-commit projection failure, restart,
   manual/rule provenance, typed values, pagination ties/bounds, and
   historical causation without fabricated readback command links.

Acceptance: every displayed Twin diff is backed by a durable transition;
raw observations do not masquerade as value transitions.

## Implementation closeout

- V22 reconciles aliases deterministically, archives every losing row, and
  changes current reported identity to `(device_id,state_key)`.
- Reported and desired transitions preserve typed values, causation, receipt
  time, correlation, and proven command identity. Same-value observation
  refreshes do not create false diffs; each accepted desired command does.
- Current state and transition history commit together. Cache projection,
  telemetry/Twin realtime, traces, events, and Rules run only after commit;
  downstream durable writes own new transactions.
- `GET /api/v1/devices/{deviceId}/twin/history` implements bounded keyset
  pagination with selector/filter-bound opaque cursors.
- The Twin Diffs view reads durable history and supports filtering and
  incremental loading. No outbox, retry subsystem, or new realtime topic was
  introduced.
