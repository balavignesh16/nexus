# P2.2 ticket — Twin transition history

Status: **planned, not implemented**. Depends on P2.1 state identity.

1. Add an indexed transition table with `transitionId`, device/state ID,
   controlled type/source, typed previous/new values and unit, applicable
   event/receipt/commit times, correlation ID and proven command ID.
2. Persist only meaningful reported typed value/unit/semantic-metadata changes
   and desired changes/clear. P2.4 may later add actual verification-status
   changes; P2.2 does not implement convergence. Newer same-value/unit/metadata
   telemetry refreshes current observation but is not a state transition.
   Replays/out-of-order/invalid
   candidates create no authoritative transition. Preserve source diagnostics
   separately. Include superseded intent in history.
3. Implement the proposed paginated, filterable `/api/v1` history route only after
   contract approval. Use stable descending `(transitionedAt,transitionId)`
   cursor order; validate limits/filter combinations. Index device/time and
   device/binding/time queries; add command index only if queried. Define
   retention and audit implications before deployment.
4. Test duplicate/out-of-order telemetry, concurrent updates, restart,
   manual/rule provenance, typed values, pagination ties/bounds, and
   historical causation without fabricated readback command links.

Acceptance: every displayed Twin diff is backed by a durable transition;
raw observations do not masquerade as value transitions.
