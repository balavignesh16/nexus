Normative requirements: [reliability-contract.md](reliability-contract.md). Execution and dependency plan: [p4-implementation-ticket.md](p4-implementation-ticket.md). This ledger owns testable scenarios and evidence status; it does not redefine the contract.

## Status discipline

- PLANNED: the required scenario or test has not been implemented and verified. Every scenario starts here.
- COVERED: only after the exact automated test and its assertions have been inspected and a successful result is recorded in the "Exact test" and "Notes" columns.
- DEFERRED: an explicitly approved deferral with reason and milestone; it is not a pass.
- Failed or incomplete evidence stays visible and is never counted complete. A planned test or a passing suite does not close an untested scenario. Assertions, timeouts, isolation and skips must not be weakened to obtain green results.
- Evidence comes only from disposable PostgreSQL and Mosquitto. The development database is never queried, migrated or repaired.

### Findings and deviations recorded while implementing P4.2

1. **Firmware and simulator duplicate behaviour (inspected, not assumed).** `firmware/src/main.cpp` `onMqttMessage` (lines 161 to 220) keeps no record of seen commandIds: a duplicate delivery of an in-window LED SET_STATE command is applied again and acknowledged again. The simulator (`command_handler.py`) does keep a bounded commandId LRU and replays the first result. Therefore duplicate suppression exists only in the simulator. P4.2 does not rely on either: it sends a command at most once (no retries), and an uncertain outcome is never resent. Exactly-once is neither implemented nor claimed.
2. **Interim failure handling before P4.3 (no retries).** Every attempt ends in a terminal state with an honest reason: confirmed in window to PUBLISHED; definite non-publication to DEAD_LETTER PERMANENT_FAILURE with last_error_code `NOT_SENT_<code>`; uncertain, late completion and lease recovery to DEAD_LETTER UNCERTAIN_EXPIRED with the ActionHistory message `DELIVERY_UNCONFIRMED`; expiry to DEAD_LETTER EXPIRED; integrity mismatch to DEAD_LETTER PAYLOAD_INTEGRITY. P4.3 replaces the transient and uncertain branches with RETRY_WAIT while attempts and time remain.
3. **Scope note.** Expiry handling and lease recovery were implemented in P4.2 (minimal, terminal-only) because without them an expired or lost command would block its device queue forever; P4.3 adds the scheduler, backoff and retry on top.
4. **Ledger wording amended (P4-004).** The original text ("with the broker stopped, acceptance still commits") contradicts contract R08.4 (a disconnected client is rejected at acceptance before any write). The scenario now states what is true and proven.
5. **Legacy backfill is conservative.** Rows younger than 5 minutes, rows with a recorded publication or ACK, rows with an outbox row and non-command rows are never classified, so a recently accepted or concurrently publishing legacy command cannot be mislabelled.
6. **Per-device order key.** Acceptance stamps `created_at` strictly after every earlier outbox row of the device (the device row lock serialises acceptances), so claim order cannot be inverted by equal timestamps.
7. **Legacy fixtures that bulk-delete devices cannot run with the flag ON.** `CommandDispatchMqttIntegrationTest` run with `nexus.command.outbox.enabled=true`: 1 of 11 passed; the other 10 errored in `@BeforeEach deviceRepository.deleteAll()` with `DEVICE_HAS_COMMAND_DELIVERY_EVIDENCE` (the V38 fail-closed guard working as designed). `ActionIntegrationTest` and `CommandAcceptanceRollbackIntegrationTest` pass with the flag ON.
8. **Phase 3 rule-command suite with the flag ON (observation, not a gate).** `RuleCommandAuthorizationIntegrationTest` (43 tests) with the flag ON: 37 pass, including every gate-denial, version, pause and ABA race test; 6 fail because they encode legacy mechanics (an immediate SUCCESS from the synchronous publish, a spy on `CommandExecutor.publishPrepared`, or a direct `publishPrepared` call after `accept`, which is exactly the bypass this slice closes). With the flag OFF (default) all 43 pass unchanged. The rule-originated flow with the flag ON is covered by `RuleOriginOutboxIntegrationTest`.

### What P4.3 built (all inside the existing dispatcher and outbox)

- `OutboxRetryPolicy` (new, pure, no SQL or clock): the single retry decision. Only a proven NOT_SENT attempt can be retried, only within the stored attempt budget, and only if the next attempt would start strictly before `expires_at` on the database clock. Backoff `min(max-backoff, initial x multiplier^(n-1))`, symmetric jitter, never below 1 ms.
- `OutboxDeliveryOperations.notSent` (the only writer of RETRY_WAIT): persists `next_attempt_at` from the database clock with the state change and the ATTEMPT_FAILED_TRANSIENT fact; exhaustion becomes DEAD_LETTER RETRY_EXHAUSTED, a window too short becomes EXPIRED. The claim and the candidate query now accept RETRY_WAIT rows; a RETRY_WAIT command blocks later commands of its device. Uncertain outcomes and lost leases stay UNCERTAIN_EXPIRED and are never retried.
- `CommandOutboxSettings.worstCaseEndToEnd`: the schedule is recomputed from the real attempt budget, backoff and jitter (3 x 3 s + 0.6 s + 1.2 s = 10.8 s) and, end to end, with one poll interval per claim and the one-second timestamp truncation (12.55 s); startup refuses a window that cannot hold it.
- Crash-safe failure signals: `unreactedFailures` and `recoverFailureSignals` re-apply only the two idempotent signals (Twin `commandFailed` only when the verification is still PENDING, one COMMAND_PUBLICATION_FAILED rule fact) for proven-not-sent dead letters whose post-commit reaction was lost; scan every 5 s; nothing is broadcast again; uncertain or acknowledged outcomes are never reported.
- Not changed: `firmware/**`, the simulator source, hardware paths, migrations V1 to V39.

## P4.4 evidence (2026-10-18)

Only the scenarios marked COVERED in the tables above are proven, each by the exact tests cited in its row. Nothing here claims that an ACK is authenticated (Phase 7), that an ACK or its absence proves anything physical, exactly-once publication or actuation, device-side deduplication or ordering, multi-process evidence, or any later slice (telemetry deduplication, backpressure, observability and the read API, integrated fault injection). **No migration was added**: V39 already holds every ACK fact type and the sources ACK_HANDLER, TIMEOUT_SCANNER and RECONCILER, so V1 to V39 are unchanged and V40 stays reserved for P4.5. The decisions the wording of R13, R14 and R16 left open are recorded in contract R34.

### What P4.4 built

- `CommandAckFacts` (new): the durable ACK facts, written by the ACTUAL `DeviceCommandAckMessageHandler` in the same transaction as its guarded ACK update. First ACK: ACK_ACCEPTED or ACK_REJECTED; late first ACK: additionally ACK_AFTER_TIMEOUT or ACK_AFTER_TERMINAL; conflicting duplicate: ACK_CONFLICT_IGNORED (at most 5 per command); identical duplicate: nothing and a counter. The ACK path only reads the outbox, takes no outbox lock, and the receipt time is the database clock.
- `CommandAckTimeoutScanner` (new): the single owner of the ACK_TIMED_OUT history fact. Database-clock eligibility, strictly after the stored deadline, serialised on the action_history row lock, one fact per command, nothing else is written.
- `LegacyDeliveryReconciler` (new): the runtime counterpart of the V39 backfill (same eligibility, grace of at least 5 minutes): DELIVERY_UNKNOWN once, nothing published, nothing else written.
- `OutboxDeliveryOperations`: the publication instant and the persisted ACK deadline now come from the database clock (the interim application-clock derivation of P4.2 is corrected); an acknowledged command is never claimed; `resolveAcknowledgedUnpublished` ends an acknowledged QUEUED or RETRY_WAIT obligation as DEAD_LETTER UNCERTAIN_EXPIRED / ACKNOWLEDGED_BEFORE_PUBLICATION without a failure signal.
- Configuration: `nexus.command.lifecycle-scanners-enabled`, `ack-timeout-scan-interval`, `legacy-reconcile-interval`, `legacy-reconcile-grace` (the scanners are always beans and do not consult the outbox flag; the test default switches only their scheduled loops off).
- Not changed: `firmware/**`, the simulator, hardware paths, migrations V1 to V39, the frontend.

### Defects found by the new tests and fixed in P4.4

1. **Double classification by concurrent reconcilers.** The first implementation re-checked the eligibility conditions in the same statement as the row lock. A locking read re-checks only the locked row, not subqueries on other tables, so a reconciler that waited for the lock still saw "no history fact" and appended a second DELIVERY_UNKNOWN. `LegacyDeliveryReconcilerTest.concurrentReconcilersMarkEachStrandedCommandExactlyOnce` reported 21 classifications for 10 commands; the conditions on other tables are now evaluated in separate statements after the lock was taken. Mutation M11 (the idempotency check removed) is killed by the same test.
2. **Ledger tests that encoded the interim state.** Three P4.2 assertions in `CommandOutboxAckHandlerIntegrationTest` stated "no ACK fact (those are P4.4)"; they now assert the delivery facts unchanged and the ACK facts appended, which is stronger.
3. **Application-clock ACK deadline (P4.2 interim).** Corrected as described above and proven with an application clock 24 hours ahead and behind.

### Limitations stated honestly

- No multi-process evidence: the concurrency tests use several connections and instances against one disposable PostgreSQL.
- The real-broker tests make a device client publish ACKs; a broker-level redelivery of an unacknowledged ACK message after a processing failure is not exercised (the rollback and the later recording are).
- An ACK is not authenticated and is not proof that anything physical happened; an ACK timeout is not proof that nothing did. The committed firmware still has no commandId deduplication.
- For legacy rows the stored acceptance timestamp is an application-clock value; an application clock more than the 5 minute grace behind could make a still-running legacy dispatch look old, with a spurious history fact as the only effect. `CommandStatus.from` still computes TIMED_OUT on read with the application clock (R14).
- A command acknowledged while QUEUED or RETRY_WAIT ends as UNCERTAIN_EXPIRED and holds its device for 40 seconds: conservative by design.
