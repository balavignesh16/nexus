## Status discipline

- PLANNED: the required scenario or test has not been implemented and verified. Every scenario starts here.
- COVERED: only after the exact automated test and its assertions have been inspected and a successful result is recorded in the "Exact test" and "Notes" columns.
- DEFERRED: an explicitly approved deferral with reason and milestone; it is not a pass.
- Failed or incomplete evidence stays visible and is never counted complete. A planned test or a passing suite does not close an untested scenario. Assertions, timeouts, isolation and skips must not be weakened to obtain green results.
- Evidence comes only from disposable PostgreSQL and Mosquitto. The development database is never queried, migrated or repaired.

### Findings and deviations recorded while implementing P4.2

1. **Firmware and simulator duplicate behaviour (inspected, not assumed).** `firmware/src/main.cpp` `onMqttMessage` (lines 161 to 220) keeps no record of seen commandIds: a duplicate delivery of an in-window LED SET_STATE command is applied again and acknowledged again. The simulator (`command_handler.py`) does keep a bounded commandId LRU and replays the first result. Therefore duplicate suppression exists only in the simulator. P4.2 does not rely on either: it sends a command at most once (no retries), and an uncertain outcome is never resent. Exactly-once is neither implemented nor claimed.
2. **Interim failure handling before P4.3 (no retries).** Every attempt ends in a terminal state with an honest reason: confirmed in window to PUBLISHED; definite non-publication to DEAD_LETTER PERMANENT_FAILURE with last_error_code `NOT_SENT_<code>`; uncertain, late completion and lease recovery to DEAD_LETTER UNCERTAIN_EXPIRED with the ActionHistory message `DELIVERY_UNCONFIRMED`; expiry to DEAD_LETTER EXPIRED; integrity mismatch to DEAD_LETTER PAYLOAD_INTEGRITY. P4.3 replaces the transient and uncertain branches with RETRY_WAIT while attempts and time remain.
3. **Scope note.** Expiry handling and lease recovery were implemented in P4.2 (minimal, terminal-only) because without them an expired or lost command would block its device queue forever; P4.3 adds the scheduler, backoff and retry on top.
4. **Ledger wording amended (P4-004).** The original text ("with the broker stopped, acceptance still commits") contradicts contract R08.4 (a disconnected client is rejected at acceptance before any write). The scenario now states what is true and proven.
5. **Legacy backfill is conservative.** Rows younger than 5 minutes, rows with a recorded publication or ACK, rows with an outbox row and non-command rows are never classified, so a recently accepted or concurrently publishing legacy command cannot be mislabelled.
6. **Per-device order key.** Acceptance stamps `created_at` strictly after every earlier outbox row of the device (the device row lock serialises acceptances), so claim order cannot be inverted by equal timestamps.
7. **Legacy fixtures that bulk-delete devices cannot run with the flag ON.** `CommandDispatchMqttIntegrationTest` run with `nexus.command.outbox.enabled=true`: 1 of 11 passed; the other 10 errored in `@BeforeEach deviceRepository.deleteAll()` with `DEVICE_HAS_COMMAND_DELIVERY_EVIDENCE` (the V38 fail-closed guard working as designed). `ActionIntegrationTest` and `CommandAcceptanceRollbackIntegrationTest` pass with the flag ON.
8. **Phase 3 rule-command suite with the flag ON (observation, not a gate).** `RuleCommandAuthorizationIntegrationTest` (43 tests) with the flag ON: 37 pass, including every gate-denial, version, pause and ABA race test; 6 fail because they encode legacy mechanics (an immediate SUCCESS from the synchronous publish, a spy on `CommandExecutor.publishPrepared`, or a direct `publishPrepared` call after `accept`, which is exactly the bypass this slice closes). ### What P4.3 built (all inside the existing dispatcher and outbox)

- `OutboxRetryPolicy` (new, pure, no SQL or clock): the single retry decision. Only a proven NOT_SENT attempt can be retried, only within the stored attempt budget, and only if the next attempt would start strictly before `expires_at` on the database clock. Backoff `min(max-backoff, initial x multiplier^(n-1))`, symmetric jitter, never below 1 ms.
- `OutboxDeliveryOperations.notSent` (the only writer of RETRY_WAIT): persists `next_attempt_at` from the database clock with the state change and the ATTEMPT_FAILED_TRANSIENT fact; exhaustion becomes DEAD_LETTER RETRY_EXHAUSTED, a window too short becomes EXPIRED. The claim and the candidate query now accept RETRY_WAIT rows; a RETRY_WAIT command blocks later commands of its device. Uncertain outcomes and lost leases stay UNCERTAIN_EXPIRED and are never retried.
- `CommandOutboxSettings.worstCaseEndToEnd`: the schedule is recomputed from the real attempt budget, backoff and jitter (3 x 3 s + 0.6 s + 1.2 s = 10.8 s) and, end to end, with one poll interval per claim and the one-second timestamp truncation (12.55 s); startup refuses a window that cannot hold it.
- Crash-safe failure signals: `unreactedFailures` and `recoverFailureSignals` re-apply only the two idempotent signals (Twin `commandFailed` only when the verification is still PENDING, one COMMAND_PUBLICATION_FAILED rule fact) for proven-not-sent dead letters whose post-commit reaction was lost; scan every 5 s; nothing is broadcast again; uncertain or acknowledged outcomes are never reported.
- Not changed: `firmware/**`, the simulator source, hardware paths, migrations V1 to V39.

## P4.6 safety repair evidence (2026-10-17, commit on `feature/p46-flow-control` after `e6d95e8`)

The targeted safety audit of P4.6 found two defects; both were repaired in a separate corrective commit. Authority: contract R36 (publish gate, clock) and R35 (telemetry locks).

### Root causes and changes

1. **Rate limiter and the application clock.** `OutboxDeliveryOperations.deadLetter` recorded `terminal_at` of an UNCERTAIN outcome (and of a publish that completed after the delivery window) from the APPLICATION clock, and `recoverExpiredLeases` did the same for a lease-recovered attempt, while `CommandPublishGate` counts such rows with `terminal_at > clock_timestamp() - 1 s` on the DATABASE clock. A host whose clock is about a second or more off the database's (the JVM and the database container differ by 1.18 s on the development machine) could record an instant the gate no longer counted, so a second publication could start inside the same second although the first may have reached the broker. The audit reproduced it (rate 1, application clock an hour behind: second claim allowed). Fix: `terminal_at` of a possibly-published attempt is now `clock_timestamp()` (three SQL spots, no other outcome and no history fact changed; payload, identity and wire timestamp untouched).
2. **F3, telemetry ingestion versus device deletion.** Identified telemetry inserted its dedupe claim (foreign key: key-share lock on the device row) before asking `prepareUpdate` for `FOR NO KEY UPDATE`, while a deletion holds that row lock and its DELETE waits for the key-share holder: a cycle, SQLSTATE `40P01`, reproduced deterministically by the audit. Fix: `DigitalTwinService.underDeviceLock` takes the per-device in-process lock and then the device row lock, in the order `prepareUpdate` uses, and identified telemetry runs its whole ingestion (claim included) inside it. Unidentified telemetry is unchanged. The row lock is requested inside the ingestion transaction (the lambda is not a proxied call, so there is no self-invocation issue); the in-process lock is reentrant and covers the claim and the Twin mutation, and is released when the ingestion body returns while the row lock stays to commit; no database/in-process inversion exists because every path takes the in-process lock first. A device that vanished before the lock is the established `ResourceNotFoundException`, so MQTT unknown-device behaviour (F2) is unchanged.
