# P4.5 tracked limitations and follow-up issues

Recorded 2026-10-17 on `feature/p45-telemetry-inbox` after the P4.5 completion audit. Documentation only: no production code was changed by this record. Authority for the first item: contract R35 (Retention) and R17.

## L1. Deduplication expires after retention (design limit, not a defect)

Telemetry deduplication protects only a message that carries a `messageId`, and only while its `inbound_message_dedupe` entry exists. The entry is purged after `nexus.retention.inbound-dedupe-hours` (default 168 hours, minimum 24). A message redelivered after that (for example after a backend outage longer than the window, because the persistent MQTT session keeps unacknowledged messages and Mosquitto sets no `persistent_client_expiration`) is accepted again. The protection is therefore not indefinite, not exactly-once, and does not apply to messages without a `messageId`, which includes everything the committed firmware sends. Any change to this (longer window, a different mechanism) needs a contract amendment.

## F1. Connection-pool exhaustion under concurrent telemetry bursts (pre-existing, open)

- Evidence: with the default pool of 10 connections, 12 concurrent telemetry submissions for one device, with no `messageId` (so not related to P4.5), made 2 fail with `CannotCreateTransactionException` after 30 s. Thread dump: every thread was in the after-commit step calling `PipelineService.recordTrace`, which needs a second connection while the first is still held.
- Reach: only concurrent HTTP bursts; the MQTT callback is single threaded.
- Suggested follow-up (not done): record the pipeline trace without a second connection, or after the connection is released; add a regression test with more threads than pool connections. Candidate slice: P4.6 (backpressure) or a dedicated fix.

## F2. Unknown or non-admitted device is retried forever over MQTT (pre-existing, open)

- Evidence: `TelemetryMQTTListener` treats `ResourceNotFoundException` (unknown device) and `IllegalStateException` (device not admitted) as transient, so the unacknowledged QoS 1 message is redelivered indefinitely for a deleted or never-registered device. The P4.5 classification test records this as the current behaviour.
- Suggested follow-up (not done): decide per case whether it is permanent (acknowledge, drop, count) or has a bounded retry window; needs a decision because a device can be registered after its first message.

## F3. Device deletion racing a live telemetry ingestion could lose a database-detected deadlock (P4.5 characteristic; RESOLVED in the P4.6 repair commit)

- Evidence: reproduced deterministically by the P4.6 targeted audit: the ingestion held the foreign key's `FOR KEY SHARE` (dedupe claim) and then asked for `FOR NO KEY UPDATE`; the deletion held `FOR NO KEY UPDATE` and its `DELETE` waited for the key-share holder; PostgreSQL aborted the deletion with SQLSTATE `40P01`. The application did not retry the aborted deletion, so it surfaced as an error; an aborted ingestion would have been a transient failure. All ingestion effects are in one transaction, so nothing escaped an abort.
- Resolution: identified telemetry takes the per-device in-process lock and the device row lock before its claim (`DigitalTwinService.underDeviceLock`, the order `prepareUpdate` uses); verified by the deterministic barrier test, the race test without the former test-only retry, the mixed identified/unidentified concurrency rounds and the negative mutations recorded in the ledger. No timeout was changed and no deadlock exception is swallowed.
- Still true: a deletion now waits for an in-flight ingestion of that device instead of failing; an unknown-device ingestion remains retried (F2).

## F1 update (P4-FINAL, 2026-10-18): stronger diagnosis, still UNRESOLVED

- A narrow repair of the pipeline-trace write (in-transaction, savepoint-guarded, no second connection) was built and tested and removed that one second-connection need, but the concurrency test on a pool of two still starved. The thread dump shows `DomainEventPersister.onEvent` (REQUIRES_NEW) called from the after-commit TwinUpdatedEvent listener, and the rule paths, also need a second connection while the first is still bound. Every after-commit consumer would have to be restructured; that is not a narrow change, so by decision D1 it was reverted. Patch, test and dump: the P4-FINAL evidence directory.
- A production pool of 10 is only affected by bursts above the pool size. (`DryRunConnectionPoolIntegrationTest` with the outbox ON first looked like this, but its cause was the fixture's own asynchronous delivery; it passes once the fixture settles.)

## F2 and L1 (unchanged by P4-FINAL)

F2 (unknown-device retry loop) and L1 (dedupe memory ends with retention, 168 h) are unchanged and tracked.
